# Goji SHADOW — Restricted Direct PostgreSQL Connection Amendment

Status: **Josh-approved design direction, 2026-09-16; staged only, not deployed or operationally verified.**
Applies to: Draft PR #4, `goji-v0.3-postgame-intelligence`.
Base specification: `2026-09-16-goji-v0.3-shadow-experience-design.md`.
Supersedes **only** its restricted PostgREST custom-role/JWT transport and associated implementation-plan credential steps. All canonical evidence, immutable observations, replay/revision, AUDIT/SHADOW/LIVE separation, validation and independent human release gates are unchanged.

## Decision and reason

The live read-only preflight found no `goji_shadow_writer`, no proven way to issue a securely signed restricted-role PostgREST JWT, and no Supabase development database. The canonical `shin2_verdicts` and `shin2_settlements` tables have RLS enabled but no SHADOW policy; service_role bypasses RLS. We will not mint a JWT, rotate production signing keys or repurpose `service_role`/`anon` for SHADOW.

Use an independent PostgreSQL **LOGIN** named `goji_shadow_writer`, connecting only from a trusted GitHub Actions job through an encrypted, certificate-verified direct PostgreSQL connection. Do not grant it membership in `postgres`, `service_role`, `authenticated`, `anon`, `authenticator`, or a privileged group. NOINHERIT alone is insufficient: inspect memberships and ability to SET ROLE. No BYPASSRLS, SUPERUSER, CREATEDB, CREATEROLE, REPLICATION, schema CREATE, TEMPORARY, or direct DML on canonical tables. A dedicated narrow NOLOGIN function-owner role may be used, with only the minimum SELECT on genuine frozen verdicts and INSERT/SELECT on SHADOW observations, enforced by reviewed table grants/RLS. The login receives EXECUTE only on individually allowlisted SHADOW functions, never arbitrary SQL privileges to alter official state. Audit any existing PUBLIC-granted functions and views before concluding isolation.

Use PostgreSQL functions with fixed signatures and parameterized inputs. If SECURITY DEFINER is demonstrably required to bridge inaccessible canonical rows, assign ownership to a dedicated non-bypass role with narrowly granted table access and set a secure search_path; do not leave a privileged postgres-owned SECURITY DEFINER function publicly executable. Revoke implicit PUBLIC execution before granting only the shadow login. Functions must check canonical prediction identity, freeze timestamp and fingerprint, supported result evidence, stable replay digest and revision linkage inside one transaction. A unique constraint and immutable UPDATE/DELETE trigger reinforce append-only behavior. No function writes or triggers into official settlement, experience, scoreboards or training tables.

Do not grant the login direct `SELECT` on entire verdicts, and do not add blanket `USING (true)` policies. If a narrow function owner needs verdict access, introduce an explicit SELECT policy restricted to that non-bypass owner and restrict returned columns/rows in the queue function. The SHADOW observation table stays isolated and RLS-enabled even if it is in public; no new Data API privileges are introduced. Confirm `PUBLIC` function grants and role memberships explicitly.

## Credential and network boundary

- The initial code requires `GOJI_SHADOW_ENABLED=true` and a separate `GOJI_SHADOW_DATABASE_URL`; it never reads or falls back to `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_SHADOW_JWT` or an administrative PostgreSQL connection string.
- Use a secrets-store-generated random password, provisioned outside migration code only after separate approval; migration may create the LOGIN without a usable password. Never commit, print, log or serialize the connection URI. Store it only as a GitHub Actions secret when authorized. Rotate/revoke separately on incident or decommission.
- Require `sslmode=verify-full` and an absolute path to the project CA certificate through `sslrootcert`. Validate the certificate hostname/chain at actual connection time; do not fall back to `sslmode=prefer` or `require`. Confirm the project's direct IPv6 endpoint or an approved session pooler is reachable from the runner; no weakening to an insecure transport. Limit connections/timeouts and enable read-only transactions for readiness/queue; record uses a separate explicit write transaction.
- SHADOW's runner receives no Supabase service-role key and has no generic SQL/RPC interface. Its three public operations are readiness, queue and append observation. Use parameterized queries against the exact named functions; never interpolate identifiers or user data into SQL.
- AUDIT remains zero-write; LIVE is disabled in the CLI/workflow for initial release; no cron. Separate production migrations, secrets provisioning, initial SHADOW writes, recurring schedule, merge and LIVE each require explicit approval. The current manual AUDIT workflow retains its existing credential only until a separately reviewed read-only audit credential replaces it; code-level no-write is not proof of credential isolation.

## Verification and release boundary

1. Stage the spec, implementation plan, safe fail-closed connection configuration, and offline tests on PR #4 only. No production SQL, roles, tokens, secrets, jobs, branches, costs or writes.
2. In a **separately approved isolated test database**, obtain a cost/availability determination before creating any paid Supabase branch. Rehearse the exact existing `2026091601_postgame_intelligence.sql` then the new append-only SHADOW migration. Provision only test credentials. Verify successful TLS `verify-full` connection and inspect actual `session_user`/`current_user`, role attributes, memberships, grants, RLS, PUBLIC execution and forbidden paths.
3. Prove narrow queue/record/readiness work, unsupported/missing evidence fails closed, replay produces one row, changed evidence is a revision, UPDATE/DELETE and canonical `genome_settle`/`genome_freeze_slate` calls fail under the login, and canonical row counts/checksums remain unchanged. Roll back and verify zero residue. A static test, CI green status, or rollback-only rehearsal is **not** a live permission proof.
4. After separate production authorization, take a verifiable recoverable checkpoint, apply migrations in order, provision a production login secret separately, and repeat the authorization checks before any initial SHADOW run. A real frozen TEAM + PLAYER_PROP slate and independent ground-truth manual AUDIT remain mandatory. Keep SHADOW disabled if no qualifying slate or no proof.
