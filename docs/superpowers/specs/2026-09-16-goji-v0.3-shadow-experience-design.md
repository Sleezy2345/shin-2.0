# Goji v0.3 — GENOME-backed SHADOW Experience Design

Status: **Design specification for Josh's review; not implemented or deployed.**
Date: 2026-09-16
Companion: `docs/superpowers/specs/2026-09-16-goji-v0.3-postgame-intelligence.md`
Integration target: Draft PR #4, branch `goji-v0.3-postgame-intelligence`, targeting `main`.

## 1. Purpose and approved scope

Let Goji accumulate verifiable, durable postgame experience over time while preserving the existing prediction/freeze contract, canonical GENOME and the production model untouched. Josh explicitly approved: (a) genuine frozen predictions only for initial collection, (b) SHADOW observations stored durably but isolated inside GENOME, (c) no pollution of official performance or training, and (d) a gated installation and human-controlled graduation process.

The first eligible inputs are real frozen TEAM and PLAYER_PROP predictions, ideally an MLB or CFB slate with both families. SHADOW never manufactures picks, reconstructs hypothetical pregame probabilities from results, or backdates a freeze. Historical predictions may be used only if a genuine, independently verifiable pregame freeze and required identities/evidence already exist. The previous preflight found no eligible unresolved real FULL_SLATE row with SportsGameOdds identity; the design must handle zero eligible inputs as a normal, honest result rather than reporting progress.

This is an extension of the existing v0.3 postgame architecture, **not** a second Goji instance or separate database. No autonomous slate construction, model training, betting automation, live betting, or automatic graduation is in scope.

## 2. Existing interfaces and the deployment defect

The Draft PR currently implements `OperationalPostgame.run(..., mode='AUDIT'|'LIVE')` in `goji/postgame.py`. AUDIT calculates proposals without GENOME writes; LIVE calls canonical GENOME settlement/review, postmortem and hypothesis/evidence RPCs. `goji/genome.py` uses a Supabase service-role credential to invoke those RPCs. The new `.github/workflows/goji-postgame.yml` schedules hourly AUDIT and exposes manual AUDIT **and LIVE**. The functions it calls are introduced by the un-applied migration `supabase/migrations/2026091601_postgame_intelligence.sql`.

Consequently, merging the workflow before migrating can activate a failing scheduled job, even though AUDIT does not write. Merely passing unit tests and a rollback-only migration rehearsal does not prove operational SHADOW correctness. Fix dependency order and eliminate the premature LIVE workflow choice before merging or enabling any schedule.

Preserve current immutable verdicts, freeze fingerprints, canonical `genome_settle`, experience-event triggers, `prediction_postmortems`, hypotheses/evidence and existing v0.2 FULL_SLATE and HIGHER/LOWER compatibility. Do not mutate a frozen prediction to make it eligible.

## 3. Modes and hard boundaries

| Mode | Reads | Permitted writes | Intended state |
| --- | --- | --- | --- |
| AUDIT | Genuine frozen predictions, finalized results and existing canonical state | None to GENOME, including no SHADOW writes | Default, inspect and compare with manual ground truth |
| SHADOW | Same frozen/result evidence and shared deterministic evaluators | Only dedicated GENOME SHADOW observation/revision/error boundary | Explicitly enabled after migration, manual checks and authorization |
| LIVE | Canonical unresolved queues, result evidence and approved production postgame state | Existing canonical settlement/review/SCARS/MOLT RPCs after separate approval | Disabled in initial SHADOW rollout |

AUDIT and SHADOW run the same result adapter, postgame CARAPACE, market evaluators, observable-evidence comparison, SCARS diagnosis and MOLT *proposal* logic. Reuse library functions, not duplicate outcome logic. SHADOW must never call `genome_settle`, `genome_mark_review_required`, `genome_record_postmortem`, `genome_register_experience_hypothesis` or `genome_record_experience_evidence`; it cannot edit production training data, canonical scoreboards, calibration, feature weights, ROAR, REACTOR, SPINES or THERMAL. Those are separate modes and code paths with explicit allowlisted write methods, not a fallback from one mode to another.

The initial GitHub workflow exposes manual AUDIT and, after prerequisites are satisfied, manual SHADOW only. Remove LIVE from the workflow's selectable options and require an independent code/config release for future LIVE. Scheduled execution is absent or hard-disabled until all installation gates pass; if enabled later, it invokes SHADOW only, never LIVE. A false/unset enable flag must fail closed.

## 4. Evidence intake and identity

Source: preexisting canonical `shin2_verdicts` frozen record with prediction ID, immutable freeze fingerprint, frozen timestamp, sport/game identity, prediction type, selection and provenance. For TEAM, require resolvable provider event identity and enough verified home/away context to grade a supported team-winner market. For PLAYER_PROP, additionally require player, market, exact line, side and matching frozen provider odd ID. A genuine frozen prediction with missing required data remains ineligible/reviewed, not guessed; a later provider value cannot be silently inserted into frozen pregame inputs.

ECHOSENSE fetches timestamped SportsGameOdds final-result evidence. CARAPACE checks finality, provider event identity, sport/team correspondence, provenance, supported exact odd ID/stat and conflicting claims; impossible timing, unresolved scratches, unsupported rules, ties or missing statistics produce UNRESOLVED or REVIEW_REQUIRED. Final score is not sufficient for arbitrary prop grading. Historical finalized data is not rejected using pregame freshness thresholds. Preserve original freeze, provider receipts, normalized evidence, evaluator/result-adapter versions and post-freeze events without overwriting what was known pregame.

For initially supported team and player-prop markets, the same production-designed deterministic evaluator returns a *proposed* WIN/LOSS/PUSH/VOID only when its rule is verified. A proposal is not a canonical settlement and cannot trigger settlement-based experience events. Unknown outcomes stay explicitly unknown. SportsGameOdds `NCAAF` maps to canonical `CFB`; HIGHER/LOWER remains compatible with OVER/UNDER. No sport receives an evidence exemption for additional coverage.

## 5. Minimal durable GENOME SHADOW boundary

Use the existing Supabase GENOME project and canonical frozen-verdict foreign key. Add only the minimal dedicated append-only SHADOW observation/revision storage and narrow read/write RPCs in an ordered, separately reviewed migration dependent on `2026091601_postgame_intelligence.sql`. Do **not** add another verdict table, another settlement table, a parallel official postmortem store or a second hypotheses/maturity engine.

Each SHADOW observation records, at minimum: immutable observation ID, prediction ID, freeze fingerprint, slate/game/sport/type, retrieval and event-source timestamps, frozen-versus-observed references, result digest and provenance, CARAPACE state/reason, proposed evaluator outcome and exact grading inputs, evaluator and adapter versions, SCARS comparison and uncertainty/learning-value fields where evidence exists, optional MOLT *proposed* hypothesis/evidence (not canonical hypotheses/evidence writes), explicit SHADOW lifecycle/eligibility, created timestamp, and source evidence identifiers. Store only necessary evidence/references and never API secrets. Freeze and outcome artifacts must be reconstructable without treating the current provider response as the original pregame snapshot.

Implement database-enforced linkage to an existing genuine frozen prediction, fingerprint equality, a unique replay key and a narrow insert-only RPC; disallow UPDATE/DELETE of observations via the application path. Create no trigger that writes `shin2_settlements`, `genome_experience_events`, `prediction_postmortems`, official scoreboards or canonical hypotheses/evidence. Check all table/view/function dependencies, grants, policies and triggers before deploying. Since the current client uses a service-role key (which can bypass RLS), application-level checks alone are **not** a credible write isolation boundary; prefer a separately scoped SHADOW credential/RPC permission model where supported, remove production-write methods from the SHADOW client surface, and explicitly test attempted forbidden writes. If least-privilege enforcement cannot be demonstrated, block automatic SHADOW deployment and disclose the residual risk rather than claiming hard isolation.

A stable replay key derives from immutable prediction ID + freeze fingerprint + evaluator version + normalized result content (excluding fetch-time-only metadata). Exact retries return the existing observation without creating extra experience or changing the original. Provider corrections or changed evaluator outputs must append a separately linked revision with a supersession/review state, not silently overwrite history. Never count original and correction as independent samples; unresolved conflicting revisions are excluded from learning-eligible counts until reviewed. Separate transient errors from durable verified evidence and retry without generating artificial samples.

Keep all SHADOW tables/RPCs out of existing canonical settlement, training, official scoreboard and hypothesis/evidence queries by default. SHADOW reports query only the isolated boundary and explicitly label their denominator. If a later promotion is approved, use a distinct, audited promotion pathway that references the immutable source observation and prevents double counting; initial v0.3 has no such automatic pathway.

## 6. Experience and reports

SHADOW may compare frozen expectations with actual observable evidence through SCARS and aggregate recurring patterns as **proposals** through MOLT. Preserve expectation quality separately from correctness; a win is not necessarily good reasoning and a loss is not automatically a model flaw. Data failures, major surprises, unresolved evidence and missing postgame observability cannot be treated as clean high-learning-value examples. Preserve source trust/conflict and post-freeze changes. Never fabricate missing expectations, player scores, win probabilities or confidence.

Reporting distinguishes: genuine frozen inputs discovered; eligible predictions; matched finalized outcomes; unambiguous proposed grades (TEAM and PLAYER_PROP separately, then combined); UNRESOLVED; REVIEW_REQUIRED; observation records/revisions; SCARS diagnoses; evidence eligible/ineligible for pattern learning; proposed MOLT hypotheses; and errors. Accuracy is shown only for clearly defined comparable verified proposed grades, labeled **SHADOW only**, with pushes/voids and unknowns separated. NO_ROAR/cold-start items lacking an actionable probability or selection cannot be represented as validated trained-model accuracy. Track independence using frozen independent group keys and shared games/context so many correlated props cannot inflate maturity. Zero eligible predictions means a zero-experience report, not a successful real-slate validation.

Official scoreboard, bankroll, probability calibration, trained/cold-start designation and production prediction outputs remain unaffected. SHADOW storage is experience accumulation, not evidence that Goji has exited cold-start.

## 7. Failure and recovery contracts

Missing credentials or migration/RPC version: stop safely with an explicit diagnostic; no fallback to LIVE and no scheduled retry loop misreported as success. Provider failure or non-final event: leave unresolved and retry later. Missing provider identity, exact odd ID, source proof or market rule: no settled grade, do not fill from postgame knowledge. Conflicting result revisions: append review metadata only through controlled revision path; never silently replace an earlier result. Database write failure: existing canonical state remains unchanged and report the SHADOW operation as failed; retry deterministically. SCARS/MOLT failure does not erase verified outcome evidence, and no invented learning record compensates for the failure. An unchanged rerun generates no additional sample. Logs and error payloads must not expose Supabase or SportsGameOdds secrets.

## 8. Deployment sequence and graduation gates

1. Keep PR #4 in Draft and `main` unchanged. Amend the PR design/implementation to hard-disable the hourly job and remove manual LIVE from the rollout workflow. Unit-test that disabled means no postgame invocation and that SHADOW cannot route to canonical write methods.
2. Inspect live database schema, existing migrations, functions, triggers, grants/RLS and canonical view contracts read-only. Write an ordered SHADOW migration/restricted RPC plus rollback strategy, preserving v0.2 and existing GENOME rows. Review migration SQL and perform a transactional rehearsal; verify zero residue. Rehearsal alone is not production authorization.
3. Implement SHADOW mode and deterministic persistence with RED/GREEN TDD, replay/conflict and failure tests, API contract tests, and full legacy regression suite. Check GitHub Actions on the exact final commit; request code review. No database writes beyond rehearsals at this step.
4. Separately request explicit production-migration approval, take/verify a recoverable schema/state checkpoint and apply migrations in dependency order. Confirm post-apply function signatures, permissions, and that canonical tables/scoreboards and existing predictions did not change. Stop on drift; no fake success reporting.
5. Run manual zero-write AUDIT on an actual completed frozen slate with both team and player props, confirm all grading against independent manual reality including ambiguous cases. If none qualifies, hold here and collect future *genuine pregame freezes* through the existing legitimate v0.2 process—do not generate retroactive inputs or auto-enable SHADOW.
6. With separate permission for isolated SHADOW writes, run manual SHADOW on that same slate. Verify immutable trace, exact retries, correction handling, forbidden-write attempts, comparison with AUDIT, and no changes to canonical settlements, experience events, scoreboards or trained-model behavior. Once these gates pass, request explicit authorization to enable recurring SHADOW collection. Enable with a kill switch and limited frequency, monitor errors and experience counts.
7. Graduation is not time-based. Accumulate independent, diverse, recent, high-quality evidence; evaluate multi-dimensional Experience Maturity (depth, independence, source quality, context, SCARS learning value, OOS validation, recency, regime). RIVAL challenges candidate lessons; ARENA tests unseen data; FOSSIL maintains recoverable trusted state. Human approval is required for every proposed promotion. LIVE settlement requires its **own** later authorization and manual-AUDIT gate, never implicit SHADOW graduation.

## 9. Acceptance criteria

- Only genuinely pregame-frozen TEAM/PLAYER_PROP records can produce SHADOW observations; missing identity/stat/mapping stays unresolved or review-required.
- AUDIT has zero database writes; SHADOW only uses scoped append-only GENOME observation/revision/error writes; LIVE is unavailable in initial scheduling/manual workflow.
- Schedules cannot execute against missing migration or secrets; feature disabled by default until the deployment sequence is completed.
- Identical retries are idempotent; corrected results are preserved without double counting; disputed corrections are not learning eligible.
- Canonical verdicts, freezes, settlements, settlement triggers/experience events, official postmortems, hypotheses/evidence, scoreboards, predictions and calibration remain unchanged by SHADOW.
- Full suite remains green and covers access-control attempts, migration dependency/drift, zero inputs, missing provenance, team/prop grading, replay, conflict, SCARS/MOLT error recovery and audit-versus-shadow consistency.
- A genuine completed slate with both prediction families matches independently verified manual results before any recurrent SHADOW run.
- Reports label SHADOW-only evidence and never misrepresent cold-start or unknown outcomes; future training, LIVE, promotion and production migrations are separately approved actions.
