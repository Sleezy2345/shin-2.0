# Goji v0.3 — Postgame Intelligence

## Goal

Make Goji able to close the loop after a frozen slate: retrieve final results, validate them conservatively, settle only unambiguous predictions through the canonical GENOME settlement path, diagnose what the result means through SCARS, form candidate lessons through MOLT, and feed those lessons into the existing Evidence Maturity system without allowing one outcome to rewrite production behavior.

The core settlement contract is sport-agnostic. Live validation starts with MLB and CFB, while NFL and future sports reuse the same interfaces once their adapters and fixtures pass the same gates.

## Non-goals

- Do not bypass the existing GENOME settlement or experience tables.
- Do not let a provider write directly to GENOME.
- Do not grade a prediction merely because a game is marked final.
- Do not guess player-prop outcomes from incomplete player-stat data.
- Do not treat a win as proof of good reasoning or a loss as proof of bad reasoning.
- Do not auto-promote MOLT lessons into REACTOR, SPINES, THERMAL, ROAR, or any other production behavior.
- Do not collapse Evidence Maturity into one opaque score.
- Do not enable autonomous LIVE settlement until AUDIT mode has matched manual reality on a completed real slate.
- Do not create duplicate SCARS/postmortem persistence when GENOME already has canonical postmortem storage.

## Existing canonical state to preserve

v0.3 must wrap the current foundation rather than duplicate it.

GENOME already provides:

- `genome_review_queue(p_slate_id)` for unresolved frozen predictions whose games have started.
- `genome_settle(p_settlement_id, p_prediction_id, p_payload, p_freeze_fingerprint)` as the canonical settlement RPC.
- Idempotent settlement behavior through the underlying settlement function: an identical retry is safe; a conflicting settlement is rejected.
- A settlement trigger that creates `genome_experience_events` from settled predictions.
- `prediction_postmortems` as append-only canonical postgame diagnosis storage with one row per prediction.
- Existing postmortem fields for expectation quality, reasoning quality, outcome informativeness, variance class, learning value, pattern-learning eligibility, evidence, provenance, and correction hypotheses.
- `genome_experience_hypotheses` with separate maturity evidence fields.
- `genome_experience_evidence` and `genome_record_experience_evidence(...)` for attaching supporting, contradicting, or neutral evidence to hypotheses.

The current `genome_review_queue` relation is a read-only unresolved-prediction view derived from frozen predictions that do not yet have a settlement. It is not a persistence mechanism for a terminal human-review decision.

The current SportsGameOdds client only normalizes event identity and start time. v0.3 therefore adds a final-result adapter before any settlement automation is considered trustworthy.

## Architecture

The canonical postgame path is:

`GENOME review queue -> ECHOSENSE result adapter -> CARAPACE result validation -> universal ResolvedOutcome -> settlement evaluator -> GENOME settle -> GENOME experience event -> SCARS postmortem -> MOLT hypothesis/evidence update -> Evidence Maturity`

Provider-specific response formats terminate at ECHOSENSE. Everything downstream consumes Goji-owned contracts.

The settlement core is sport-agnostic. Sport and market differences are isolated behind evaluators rather than embedded as one growing conditional tree.

## Universal result contract

ECHOSENSE converts provider responses into a normalized result object such as `ResolvedOutcome`.

A resolved result must preserve at least:

- provider event/result identifier
- `game_id`
- `sport`
- finality/status
- home team identity
- away team identity
- final home score
- final away score
- player-stat evidence when available
- source/provider name
- provider source identifier
- observed timestamp
- provenance and raw/reference metadata needed for audit

Player-stat evidence must be keyed clearly enough for a market evaluator to retrieve the exact stat needed for a frozen prop. Missing or ambiguous stat evidence is not equivalent to zero.

The normalized result object is evidence, not a settlement decision.

## Result CARAPACE

Postgame CARAPACE validates result evidence independently from pregame CARAPACE.

A result is blocked from settlement when any of the following are true:

- the event is not definitively final
- `game_id`, sport, or team identity does not match the frozen prediction context
- required score fields are missing or malformed
- provenance is missing
- source timestamps are impossible, materially future-dated, internally inconsistent, or otherwise fail the postgame freshness policy
- credible sources disagree on a settlement-relevant fact
- the market-specific evidence needed to grade the prediction is missing
- a player prop lacks the exact player/stat evidence required by its frozen market

Postgame freshness is distinct from pregame freshness. The age of a completed game by itself must not invalidate an otherwise authoritative final result. Freshness checks protect against stale provider snapshots, impossible timing, and unresolved corrections; they do not impose the v0.2 pregame 30/90-minute thresholds on historical finals.

A final event can therefore remain `UNRESOLVED`.

When the event is final but the evidence is materially ambiguous, the pipeline returns `REVIEW_REQUIRED` rather than forcing a grade.

No downstream SCARS or MOLT processing occurs for unresolved or review-required items.

## Settlement evaluators

Settlement logic is split by prediction family behind a common interface.

### Team evaluator

The team evaluator grades a frozen team selection from verified final score and team identity.

It may emit:

- `WIN`
- `LOSS`
- `PUSH` when the frozen market supports a push condition
- `VOID` when the market/rules require no contest or equivalent treatment
- `REVIEW_REQUIRED` when grading is not deterministic from verified evidence

### Player-prop evaluator

The player-prop evaluator requires the frozen:

- player
- market
- line
- side
- game identity

It also requires the exact verified final player statistic for that market.

It must never infer a missing stat, assume a missing record means zero, or settle from unrelated box-score fields.

Supported prop markets are explicit. An unknown or unmapped market returns `REVIEW_REQUIRED` rather than guessing.

### Future evaluators

Additional markets may implement the same evaluator contract without changing the settlement orchestrator.

## Settlement safety contract

A prediction is eligible for settlement only when:

1. It exists in the canonical GENOME unresolved queue or equivalent frozen state.
2. Its frozen fingerprint is available.
3. The result adapter produced a matching normalized result.
4. Result CARAPACE approved the relevant evidence.
5. A market evaluator produced an unambiguous settlement outcome.

The settlement payload records enough evidence to reconstruct the grade, including:

- outcome
- final result identity
- grading inputs
- source/provider
- observed timestamp
- provenance
- evaluator type/version
- any market-specific final stat

The existing `genome_settle(...)` RPC remains the only canonical production write for settled outcomes.

Re-running the worker must be idempotent. Identical settlement attempts are harmless. A conflicting second settlement is an error and must be surfaced for review rather than overwritten.

## Review-required persistence

`REVIEW_REQUIRED` is not a settlement outcome and must not be inserted into `shin2_settlements`, because doing so would incorrectly create a canonical experience event.

v0.3 therefore adds one minimal GENOME review registry for ambiguous postgame items. It is part of GENOME, not a second persistence layer.

The review record must preserve at least:

- `prediction_id`
- `slate_id`
- review state
- reason code(s)
- evidence/provenance summary
- observed timestamp
- evaluator/result-adapter version
- optional resolution metadata when a human later settles or voids the item

The write contract must be idempotent for identical repeated review decisions and reject contradictory mutation without an explicit resolution path.

The unresolved queue and slate-completion query must account for this registry so a known review-required item is not repeatedly rediscovered as if it were unseen.

## AUDIT and LIVE modes

v0.3 introduces two execution modes.

### AUDIT

AUDIT mode runs the complete postgame decision path but performs zero canonical settlement writes and zero review-registry writes.

It reports, per unresolved prediction:

- matched result or no match
- CARAPACE decision
- evaluator decision
- proposed outcome
- proposed settlement payload
- proposed review-required record when applicable
- unresolved/review reason when blocked

AUDIT is the mandatory first production stage.

### LIVE

LIVE mode may call `genome_settle(...)` or persist a review-required item only after AUDIT has been validated on a completed real slate and the release owner explicitly enables LIVE mode.

LIVE mode does not weaken any validation rule. It differs from AUDIT only in performing approved canonical writes.

## SCARS diagnosis and canonical postmortems

Settlement answers what happened. SCARS answers what the result means.

For every canonical settled prediction, SCARS produces exactly one canonical postmortem in the existing append-only `prediction_postmortems` table. No parallel SCARS table is introduced.

Because `prediction_postmortems` is append-only and unique by `prediction_id`, v0.3 must expose an idempotent write boundary for SCARS: an identical retry is safe; a conflicting second diagnosis is rejected for review rather than mutating the original postmortem.

SCARS fills the existing structured fields rather than inventing a second schema, including:

- expected state
- actual state
- deltas
- primary/secondary failure factors
- data quality
- confidence/calibration assessment
- evidence and provenance
- expectation quality
- reasoning quality
- outcome informativeness
- variance class
- learning value
- eligibility for pattern learning
- correction hypothesis / learning notes

SCARS classifies at least these semantic cases:

- correct + expectations accurate
- correct + expectations poor
- incorrect + expectations accurate
- incorrect + expectations poor
- data/validation failure
- unexpected event
- insufficient evidence for meaningful diagnosis

These semantic cases map onto the canonical postmortem fields; they do not replace them.

This prevents a lucky win from becoming positive reasoning evidence and prevents a variance-driven loss from being treated as an automatic model flaw.

## Expectation error

SCARS compares the frozen pregame expectation state against observed reality when appropriate evidence exists.

Expectation error may be assessed at component level, for example:

- starting pitcher expectation
- bullpen availability/freshness expectation
- lineup or role expectation
- player opportunity/usage expectation
- matchup context
- weather/park context
- any other frozen SPINES feature family with an observable postgame counterpart

Missing postgame observability does not become a fabricated error score.

SCARS preserves both:

- outcome correctness
- expectation quality

These remain separate dimensions.

## Learning value

Each SCARS postmortem may assign a bounded learning value reflecting how informative that settled observation is for future learning.

Learning value should consider:

- evidence quality
- independence from previously recorded evidence
- relevance to the hypothesis/segment
- whether the observed result genuinely tested the frozen expectation
- presence of unexpected events or contamination

Learning value is evidence metadata, not permission to alter production behavior.

## MOLT pattern formation

MOLT consumes completed SCARS postmortems marked eligible for pattern learning and looks for recurring patterns across independent evidence.

MOLT may only:

1. create a candidate hypothesis
2. attach supporting, contradicting, or neutral evidence to an existing hypothesis
3. recommend an existing hypothesis for review

MOLT must not directly change production model logic, feature weights, calibration, or ROAR policy.

Example hypothesis:

`Goji is overrating MLB bullpen freshness after consecutive high-leverage usage.`

That statement begins as a hypothesis, not a production rule.

## Evidence Maturity lifecycle

Hypotheses follow the canonical lifecycle:

`Observed -> Candidate -> Supported -> Validated -> Mature`

Side states include at least:

- `Contested`
- `Decaying`

Maturity remains multi-dimensional. GENOME stores and evaluates separate evidence components including:

- sample depth
- independence
- source quality
- context coverage
- SCARS learning value
- out-of-sample validation
- recency
- regime state

No single aggregate mystery score may replace these fields.

Promotion remains:

`SCARS evidence -> MOLT hypothesis -> RIVAL challenge -> ARENA unseen-data validation -> FOSSIL promotion -> human approval -> production change`

Contradicting evidence must be able to weaken, contest, or decay a hypothesis.

## Experience decay and regime awareness

Older evidence loses influence over time according to the existing Experience Decay concept.

A detected regime change can reduce the relevance of older evidence even when the historical sample is large.

MOLT and Evidence Maturity therefore evaluate not only how much evidence exists, but whether it remains representative of the current environment.

## Automation model

Postgame automation is separate from pregame freeze.

A scheduled GitHub workflow plus manual dispatch is the intended orchestration boundary.

Each run:

1. queries GENOME for unresolved predictions not already terminal in the review registry
2. retrieves matching final-result evidence
3. normalizes provider data through ECHOSENSE
4. validates results through CARAPACE
5. evaluates only supported prediction markets
6. in AUDIT mode, reports proposed actions without writes
7. in LIVE mode, settles only unambiguous items through `genome_settle(...)` and persists terminal review-required items through the GENOME review boundary
8. processes new canonical settlements through SCARS
9. writes one canonical postmortem per eligible settled prediction
10. sends pattern-learning-eligible SCARS evidence to MOLT/Evidence Maturity
11. exits cleanly when nothing is ready

The worker is safe to rerun and must not mutate frozen pregame predictions.

## Slate completion state

A frozen slate is postgame-complete only when every prediction is in one of these terminal postgame states:

- `SETTLED`, with settlement payload outcome `WIN`, `LOSS`, `PUSH`, or `VOID`
- `REVIEW_REQUIRED`, persisted in the GENOME review registry

Predictions that are still waiting on final or sufficient evidence keep the slate open.

A completed slate may produce a postgame report containing:

- every team prediction graded individually
- every player prop graded individually
- wins, losses, pushes, voids, and review-required items
- accuracy for eligible settled predictions
- calibration/Brier context when valid
- SCARS diagnoses
- expectation-error findings
- MOLT candidate hypotheses or evidence updates
- unresolved review notes

The report must not hide unresolved or review-required items to inflate apparent completion or accuracy.

## Sport rollout

The result and settlement interfaces are sport-agnostic from the start.

Initial live-validation scope:

- MLB
- CFB

NFL and later sports graduate onto the same path only after:

- provider result fixtures exist
- team grading tests pass
- relevant prop/stat mappings pass
- ambiguous cases remain blocked
- AUDIT output matches manual reality

No sport gets a lower evidence standard merely to increase coverage.

## Error handling

Provider/network failure:
- no canonical write
- item remains unresolved
- retry later

Malformed provider result:
- CARAPACE blocks
- no settlement write

Event not final:
- unresolved
- no settlement write

Identity mismatch:
- review/block
- no settlement write

Missing player-stat evidence:
- review/block
- no settlement write

Unknown prop market:
- `REVIEW_REQUIRED`
- no settlement write

Duplicate identical settlement:
- treated as safe/idempotent

Conflicting settlement:
- surface error
- never overwrite canonical GENOME state

Duplicate identical postmortem:
- treated as safe/idempotent at the SCARS write boundary

Conflicting postmortem:
- reject and surface for review
- never mutate the append-only canonical record

SCARS failure after settlement:
- canonical settlement remains valid
- diagnosis remains pending/retryable
- no fabricated learning evidence

MOLT failure:
- existing settlement and SCARS postmortem remain valid
- no production behavior changes

## Testing strategy

v0.3 requires tests at each boundary.

### Result adapter tests

- valid final team result
- non-final event
- malformed scores
- identity mismatch
- provenance preserved
- historical final is not rejected merely because the game is old
- impossible/future provider observation time is rejected
- player-stat evidence normalized when present

### CARAPACE tests

- final valid result passes
- non-final blocks
- missing provenance blocks
- conflicting evidence requires review
- missing market-specific evidence blocks/reviews
- postgame freshness does not reuse pregame thresholds

### Evaluator tests

- team win/loss
- push/void where applicable
- valid over/under player prop
- exact-line push when market rules support it
- missing player stat
- unknown prop market
- scratched/participation edge cases where rules do not permit deterministic settlement

### Orchestrator tests

- AUDIT performs zero settlement and review-registry writes
- LIVE writes only settleable or explicit review-required terminal decisions
- unresolved items remain unresolved
- review-required items are not inserted as settlements
- retry is deterministic
- conflicting canonical settlement is surfaced
- known review-required items are not rediscovered as unseen work

### SCARS tests

- right result / right reason
- right result / wrong reason
- wrong result / sound expectation
- wrong result / poor expectation
- unexpected event
- data failure
- insufficient diagnostic evidence
- exactly one canonical postmortem per prediction
- identical retry is safe
- conflicting retry cannot mutate append-only history

### MOLT / maturity tests

- one outcome cannot promote a lesson
- repeated dependent evidence does not count as independent depth
- contradicting evidence is preserved
- stale evidence can decay
- regime change can reduce relevance
- human approval remains required for production promotion

## Release and tomorrow-readiness criteria

v0.3 is implementation-ready when the written design is approved.

v0.3 is merge-ready only when:

1. All existing v0.2 tests remain green.
2. Result normalization is provider-isolated and sport-agnostic downstream.
3. MLB and CFB fixtures cover representative final-result cases.
4. Team evaluator grading is deterministic and tested.
5. Player props settle only from exact supported stat evidence.
6. Ambiguous and unsupported cases produce `REVIEW_REQUIRED` or remain unresolved.
7. AUDIT mode proves zero settlement and review-registry writes.
8. LIVE mode uses only the canonical `genome_settle(...)` path for settlements.
9. `REVIEW_REQUIRED` is persisted separately from settlements and cannot generate training experience.
10. Duplicate identical settlement is harmless and conflicting settlement is rejected.
11. SCARS writes the existing append-only `prediction_postmortems` contract rather than a duplicate store.
12. SCARS keeps outcome correctness separate from expectation quality.
13. MOLT cannot change production behavior directly.
14. Evidence Maturity preserves separate maturity dimensions and human approval.
15. Full CI is green before merge.

v0.3 is LIVE-ready only after:

1. A completed real slate has been run through AUDIT.
2. Goji's proposed settlements match manual reality for that slate.
3. Every ambiguous item was blocked or marked review-required rather than guessed.
4. The release owner explicitly enables LIVE settlement.

## Success condition

The first successful v0.3 production cycle is:

`frozen prediction -> verified final result -> guarded grading -> canonical GENOME settlement or review-required decision -> experience event for true settlements only -> SCARS postmortem -> MOLT candidate/evidence update -> no automatic promotion`

Goji should be able to complete that chain repeatedly without modifying the frozen pregame record, fabricating missing evidence, duplicating canonical memory, or teaching itself from one noisy outcome.
